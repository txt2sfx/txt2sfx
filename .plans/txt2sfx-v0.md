## 0. Что это за проект

Опенсорс-инструмент: текстовое описание звукового эффекта → **компактный процедурный
код Web Audio API** (300–1000 байт, zero-dependency), а не аудиофайл. Философия
скопирована с img2threejs — *reconstruction-by-code*.

Четыре принципа, обязательные для всех архитектурных решений:

1. **Scripts enforce, the model judges.** Парсинг, валидация, рендер, метрики, скоринг —
   детерминированный код без LLM. LLM участвует только в проектировании структуры звука
   и оценке перцептивного сходства.
2. **Spec-first, fail fast.** Кодогенерация не стартует, пока спека не прошла валидатор
   физических инвариантов. Никогда не чинить сгенерированный JS — чинится soundline,
   JS перегенерируется.
3. **Разделение структуры и чисел.** LLM проектирует топологию (слои, примитивы, роли);
   точные числа подбирает численный оптимизатор против целевого акустического профиля.
4. **Выход — читаемый текст.** Единица обмена — формат `soundline`, диффабельный.

Никаких облачных text-to-audio моделей (Stable Audio, ElevenLabs) в ядре. CLAP-судья —
опциональный плагин, в v0 достаточно интерфейса-заглушки.

### Требование заказчика по ключам и локальности

- Тестирование идёт через **Gemini по API-ключу, который вставляется прямо в плейграунде**,
  и через **Opus 5 из CLI / по API / через MCP**.
- Внешний агент пользователя должен воспользоваться библиотекой и накопленной базой
  рецептов **максимально быстро и без установки**.
- LLM всегда пользовательская; если привлекается локальная модель генерации звука —
  она тоже исполняется на машине пользователя. Ничего не проксируется через наш сервис.

## 1. Как поднять окружение на новой машине

```powershell
# требуется Node >= 20 (проверено на v24.15.0 и v25.2.1)
npm install -g pnpm@10     # см. примечание про corepack ниже
cd <repo>
pnpm install
pnpm vitest run            # 220 тестов должны быть зелёными
pnpm build                 # tsc -b packages/shared packages/core
pnpm dev                   # плейграунд на http://localhost:5173
```

Примечания:

- **Corepack удалён из Node 25**, поэтому описанный ранее обход `corepack pnpm <cmd>`
  больше не работает: бинарника `corepack` в `C:\Program Files\nodejs` просто нет.
  Рабочий способ — поставить pnpm глобально через npm (`npm install -g pnpm@10`),
  права администратора не нужны.
- В `package.json` уже прописан `pnpm.onlyBuiltDependencies: ["esbuild"]`;
  предупреждение «Ignored build scripts: esbuild» безвредно, vitest работает.
- `node-web-audio-api` — **devDependency воркспейса**, не зависимость `core`.
  Ядро получает фабрику `OfflineAudioContext` инжекцией (см. §5).
- `.gitattributes` форсит `eol=lf` — без него round-trip тесты на Windows падают.
- Типизация тестов проверяется отдельным вызовом: `tsc -b` покрывает только `src`.
  Постоянный `tsconfig.test.json` — задача фазы 7; до неё проверять одноразовым
  конфигом с `include: ["packages/*/src", "packages/*/test"]` и `paths` на
  `@txt2sfx/{shared,core}` → `src/index.ts`.

## 3. Замороженные решения (не переоткрывать без причины)

Все они уже отражены в коде; при написании `docs/SOUNDLINE_GRAMMAR.md` их надо перенести
в документацию.

1. **Заголовок:** `sound "<имя>" <длительность> [<категория>] [loop]`.
   Категория — из закрытого списка `pop|ui|laser|impact|explosion|pickup|foley|cycle|misc`;
   без неё валидатору фазы 3 не к чему привязать инварианты. `misc` — дефолт, при
   сериализации опускается. `loop` — отдельный флаг; категория зациклённых звуков `cycle`
   (валидатор фазы 3 требует для неё флаг `loop`).
2. **Сигнальный порядок:** `source → envelope → chain → mix`, хотя пишется
   `source >> chain | envelope`. Огибающая шейпит источник, эффекты идут после неё,
   поэтому хвосты `delay`/`verb` переживают `decay`. На этом построен helicopter
   (ротор = сабовый удар, рециркулированный delay-петлёй; LFO в v0 нет).
   **Компилятор фазы 2 обязан следовать этому порядку.**
3. **Числа хранятся как написаны** (`1.2kHz` = 1.2 + unit `kHz`), конвертация только
   через `toHz/toMs/toLinear`. Это и даёт lossless round-trip.
4. **Слитные безразмерные параметры** (`Q6`) — только для закрытого набора имён из
   сигнатур (kind `ratio`/`level`). Поэтому слой `snap2` остаётся одним идентификатором.
   Сериализатор склеивает только односимвольные имена в верхнем регистре (`Q6`),
   остальное через пробел (`gain 0.9`).
5. **Ошибки построчные:** одна сломанная строка не прячет остальные
   (`parseWithDiagnostics`). Лексические ошибки прерывают разбор целиком.
   Формат сообщения: `line L, col C: <detail> (<hint>)` — идёт в LLM как есть.
6. **Словарь синонимов в подсказках** (`lowpass→lp`, `reverb→verb`, `sweep→chirp`,
   `release→decay`, `volume→gain`, ...) + Дамерау-Левенштейн для опечаток
   (`nosie→noise`). Расстояние `lowpass`→`lp` = 5, чистая метрика такое не ловит,
   а LLM ошибается именно так. Каждый пойманный синоним экономит итерацию агента.
7. **В AST попадают только явно написанные аргументы**; дефолты применяет компилятор.
   Иначе round-trip перестаёт быть побайтовым.
8. **Канонизация:** 2 пробела отступа слоя, аргументы в порядке сигнатуры, огибающая
   в порядке `gain attack hold decay curve delay`, комментарии сохраняются
   (файловые, построчные над слоем и хвостовые), пустые строки съедаются.

## 5. Фаза 2 — примитивы, компиляция, рендер, кодоген (готово)

### 5.1. Главное решение: промежуточное представление вместо двух бэкендов

ТЗ предполагало, что `graph.ts` собирает живые узлы, а `codegen.ts` независимо печатает
строки. Это означало бы **две реализации одного DSP** — 8 примитивов и 6 эффектов,
написанных дважды и обязанных совпадать до сэмпла. Они бы разошлись.

Поэтому DSP живёт в одном месте. Введён `compile/ir.ts` — `AudioIR`, описание графа,
независимое от sample rate и от наличия аудиостека. Примитивы и эффекты эмитят IR;
оба бэкенда — тупые проигрыватели: `graph.ts` инстанцирует, `codegen.ts` печатает.
Тест паритета проверяет **два проигрывателя**, а не две копии синтеза, — и потому
может требовать не «совпадения RMS в пределах допуска», а **побайтового равенства
рендеров**. На всех 10 примерах `maxAbsDiff === 0`.

Следствия, важные для следующих фаз:

- `PrimitiveDef.build(args, ctx)` вместо `build(ctx, args, when, durationMs)`:
  `BuildContext` несёт `ir`, `seed`, `start`, `stop`. Никакого `AudioContext`.
- Времена в IR — секунды **относительно онсета звука**; `when` добавляет бэкенд,
  потому что экспортируемая функция принимает его аргументом.
- `quantizeIR` округляет все числа до 6 знаков после запятой. Это не косметика:
  без округления экспорт нёс бы `0.191891363534` и либо распухал, либо округлял —
  а округлённая длина буфера в экспорте сдвигает все сэмплы относительно эталона.
  Округление один раз, до обоих бэкендов, и есть причина, по которой паритет точный.

### 5.2. Отклонения от ТЗ и их причины

| Что | ТЗ | Сделано | Почему |
| --- | --- | --- | --- |
| `modal` | 2–5 биквад-резонаторов | аддитивный синтез в буфер | Уровень резонатора, возбуждённого бёрстом, не предсказуем из soundline, а непредсказуемый уровень источника ломает инвариант `peak ≤ 0.95`, под который откалиброваны примеры. Акустика та же: партиал звенит на `freq * ratio`, затухает с `tau = Q/(pi*f)`; сумма делится на сумму амплитуд, поэтому пик буфера **доказуемо ≤ 1**. |
| `click` | «одиночный импульс» | оконный шумовой бёрст | Дирак не несёт энергии при разумном gain, униполярный «бугор» — это DC-удар, смещающий все замеры пика ниже по конвейеру. Бёрст широкополосен, имеет нулевое среднее, и `width` делает ровно то, что обещает грамматика: шире = больше низа = глуше. |
| PRNG | «свой seeded PRNG» | MINSTD (`s*16807 % 2^31-1`) | Лучше 32-битного LCG (полный период, нет слабых младших битов) **и** короче в экспорте: не нужен `Math.imul`, так как `2^31 * 16807 < 2^53`. 17 байт экономии в каждом из четырёх генераторов. Состояние не должно достигать 0 — за это отвечает `normalizeSeed` в `IRBuilder.buffer()`. |
| `pluck` | KS-петля или предрасчёт | предрасчёт буфера | Как и разрешало ТЗ: экспорту не нужны `DelayNode`, петля обратной связи и её обвязка. |

Прочие принятые решения (обоснования — в TSDoc соответствующих файлов):

- Порядок сигнала `source → envelope → chain → mix` соблюдён; хвосты `delay`/`verb`
  переживают `decay` и учитываются в `soundDurationMs` (`compile/duration.ts`).
- Атака всегда линейная (экспонента не может начинаться с нуля, а старт не с нуля щёлкает);
  спад по умолчанию экспоненциальный до `GLOBAL_LIMITS.minExpTarget` — **абсолютного**
  порога -60 dBFS, а не относительного, иначе тихие слои затухали бы дольше громких.
- Все экспоненциальные рампы клампятся от нуля (`safeExpTarget`), в том числе когда
  модель пишет `-> 0Hz` или `index -> 0`: намерение слышимо, литеральный ноль — нет.
- `dist`/`delay`/`verb` при `mix 0` не строят wet-путь, при `mix 1` — не строят
  сумматор. Оба края встречаются (`mix 1` — это helicopter), каждый сэкономленный
  узел стоит байтов в экспорте.
- Сиды слоёв разведены умножающим хешем по индексу слоя: два слоя белого шума с общим
  сидом дали бы не более широкую текстуру, а на 6 дБ громче ту же.
- Рендер **сообщает** о клиппинге (`clipped`), но никогда не нормализует: нормализация
  спрятала бы проблему там, где её ещё можно починить правильно — в спеке (принцип 2).

### 5.3. Замеренные пики: правка примеров не потребовалась

ТЗ предупреждало, что в `explosion` сумма gain четырёх слоёв ≈ 1.63, и требовало
подкрутить gain по факту замера. Замер (seed по умолчанию, 44.1 kHz):

| пример | пик | пример | пик |
| --- | --- | --- | --- |
| bubble-pop | 0.859 | helicopter | 0.505 |
| coin | 0.498 | laser | 0.818 |
| door-creak | 0.283 | powerup | 0.418 |
| explosion | 0.744 | sword-clash | 0.436 |
| footstep-gravel | 0.355 | ui-click | 0.397 |

Клиппинга нет ни в одном примере: слои не выходят на пик одновременно — их разводят
разные атаки, спады и `delay`. Сумма gain — не верхняя граница пика; **и не нижняя**:
`hp` дифференцирует, поэтому фильтр может поднять пик выше входного (есть отдельный
тест, фиксирующий это). Отсюда практический вывод для фазы 3: инвариант `maxPeak`
проверяется только на рендере, аналитически из спеки он не выводится.

Осторожно при работе над фазой 4: у `explosion` запас всего ~2 дБ, и оптимизатор,
крутящий слоты, может его съесть. Пик стоит считать частью fitness или хотя бы
проверять после оптимизации.

### 5.4. Размер экспорта: 1 KB достигнут не для всех примеров

`GLOBAL_LIMITS.maxExportBytes` = 1024. Фактические размеры после оптимизации эмиттера:

| пример | слоёв | байт | | пример | слоёв | байт |
| --- | --- | --- | --- | --- | --- | --- |
| coin | 2 | **531** | | helicopter | 3 | 1093 |
| laser | 2 | **553** | | powerup | 3 | 1169 |
| ui-click | 2 | **811** | | door-creak | 3 | 1185 |
| bubble-pop | 2 | **824** | | explosion | 4 | 1458 |
| | | | | sword-clash | 3 | 1579 |
| | | | | footstep-gravel | 3 | 1708 |

**Все четыре двухслойных примера укладываются в 1 KB; трёх- и четырёхслойные — нет,
превышение от 7% до 67%.** Причина структурная, а не в небрежной генерации: фиксированную
стоимость составляют процедурные генераторы буферов, и это ровно та цена, за которую
проект не тащит ни одного ассета. `footstep-gravel` платит за генератор шума (два цвета),
модальный банк и кривую вейвшейпера сразу — ~640 байт до первого узла графа.

Что уже сделано для размера (снизило пики размеров на 15–25%): один общий `const` на всю
прелюдию (легально — список `const` инициализируется слева направо); генераторы шума
эмитятся **по фактически использованным цветам**; односимвольные алиасы для длинных имён
методов `AudioParam`, для `connect`, для пары `start`/`stop` и для повторяющихся фабрик
`ctx.createX()` — каждый только когда окупает собственное объявление; значения, равные
дефолтам Web Audio (`gain` 1, `Q` 1, синусный осциллятор), не пишутся вовсе; параметр
с единственным `set`-событием пишется как `.value=`.

Дальнейшие идеи исчерпаны: цепочки `a.connect(b).connect(c)` дают ~3 байта на звено,
общий envelope-хелпер сэкономил бы ~20 байт на слой, но закодировал бы форму огибающей
во втором месте и обрушил бы то самое свойство, из которого следует точный паритет.

**Решение:** `withinBudget` — это отчёт, а не запрет. `codegen` возвращает `bytes` и
`withinBudget`, но всегда отдаёт полный работающий код: молча урезать экспорт или
отказаться его выдавать было бы хуже, чем сказать вызывающему, сколько он стоит.
В тестах зафиксированы (а) потолок размера на каждый пример как защита от регрессий и
(б) требование `withinBudget` для всех сооружений в ≤ 2 слоя. Для README (фаза 7) честная
формулировка — «300–1000 байт для типичного SFX», а не «всегда меньше килобайта».

### 5.5. Ещё один вход для фазы 3

`helicopter` реально звучит **4046 мс** при заявленных в заголовке 1500: `delay 90ms`
с `feedback 0.88` спадает до -60 дБ за 54 повтора. Это не баг рендера, а именно тот
случай, который валидатор фазы 3 обязан поймать по контракту длительности заголовка.
`soundDurationMs(ast)` уже возвращает 4046 и готов к использованию как есть.
Оценка хвоста ограничена сверху 4000 мс на эффект (`delay.ts`), чтобы `feedback 0.95`
не просил минуту аудио; правду при этом сообщает валидатор, а не гигантский буфер.

### 6.1. Валидатор: правила и решения

11 правил в `INVARIANTS` (массив, чтобы фаза 7 могла добавлять свои), два входа:

- `validate(ast)` — всё, что выводится из текста;
- `validateRender({ peak })` — только то, что нельзя вывести (§5.3). Отдельный тип
  `RenderFacts`, а не `RenderResult`: у оптимизатора и плейграунда есть пик без
  `AudioBuffer`, а анализатору надо уметь давать те же числа по декодированному
  референсу.

Идентификаторы правил: `<cat>.{min,max}-duration`, `<cat>.max-layer-decay`,
`<cat>.max-freq-ramp`, `<cat>.max-layers`, `cycle.requires-loop`, `duration.contract`,
`envelope.attack-longer-than-voice`, `param.range`, `param.slot-range`,
`ramp.exp-to-zero`, `pop.rising-resonance`, `peak.max`, `peak.silent`.

Принятые решения:

1. **Severity по величине отклонения** — у контракта длительности и у
   attack-vs-voice. Оба сравнивают с *оценкой*, а не с замером: хвост — экспонента,
   приведённая к -60 дБ, хвост эффекта — формула с потолком 4 с. Пара процентов —
   это шум оценки, а не ложь; в два раза — уже другой звук. Порог: слack
   `max(10 мс, 5 %)` — чисто; до 25 % — `warn`; свыше — `error`.
2. **`param.range` — error, хотя границы в сигнатурах названы «soft».** «Soft»
   описывает происхождение чисел (вкус и практика), а не серьёзность нарушения.
   `Q 400` на биквадре звенит колоколом, осциллятор на 19 кГц не слышен половине
   аудитории, а warn, который цикл агента вправе проигнорировать, стоил бы итерации
   на то же самое открытие.
3. **Исключение: `-> 0` в конце рампы не считается выходом за границу.**
   `-> 0Hz` и `index -> 0` — поддержанная идиома «свести в ничто», компилятор
   специально клампит экспоненту от нуля (§5.2), и `ramp.exp-to-zero` уже говорит,
   что реально произойдёт, лучше, чем жалоба на диапазон. Голова рампы с нулём —
   по-прежнему error. Тест на отсутствие двойного отчёта есть.
4. **`param.slot-range` — warn.** Слот, выходящий за границу параметра, — это
   разрешение оптимизатору генерировать невалидный звук; узнать об этом лучше здесь,
   чем в фазе 4 через тысячу кандидатов. Но seed легален и звук рендерится, поэтому
   не error.
5. **`peak.silent` (warn, порог 0.02 ≈ -34 dBFS) добавлен сверх ТЗ.** Ровно тот
   класс провала, который §11 назвал самым дорогим: слой на -41 дБ без единой
   ошибки. Рецепт, рендерящийся в тишину, не бывает тем, что просили.
6. **Только перерасход контракта, не недобор.** Заголовок на 1500 мс при 40 мс
   звука — тоже ложь, но ТЗ просило ловить выход за контракт, а не недоиспользование;
   отдельного правила нет сознательно.

### 6.2. Два примера не проходят валидацию — и это правда, а не баг правил

8 из 10 рецептов чисты. Два — нет, оба по `duration.contract`:

| рецепт | заявлено | реально | перерасход | severity |
| --- | --- | --- | --- | --- |
| helicopter | 1500 мс | 4046 мс | 170 % | **error** |
| sword-clash | 700 мс | 821 мс | 17 % | warn |

`helicopter` — тот самый предсказанный §5.5 случай. Важно: **его нельзя привести в
контракт правкой одного заголовка** — 4046 мс выходит за собственный потолок категории
`cycle` (3000 мс). Находка зафиксирована тестом, а не заглажена: это решение звукового
дизайна, а не рефакторинг.

**Три рычага, решение за заказчиком:**

1. Принять как есть — тест это пинует, сюрприза не будет.
2. Менять DSP: `delay 90ms feedback 0.88` — это и есть ротор (§3.2); чтобы хвост
   уложился в 1450 мс, нужен `feedback ≤ 0.65`, то есть другой звук.
3. Поднять `CATEGORY_LIMITS.cycle.maxDurationMs` с 3000 до ~4500 и заголовок до 4046.
   Законный вариант: шапка `constants.ts` прямо называет эти числа мнением проекта, а
   обоснование «редко превышают три секунды» — про период петли, не про хвост
   рециркуляции. Если 4-секундный разгон ротора и есть правильный звук, сдвинуть
   границу дешевле, чем портить рецепт.

**Дедлайн решения — фаза 5, не конец работ.** `POST /api/recipes` по §8 валидирует
soundline перед записью, а `seed.ts` заливает все `examples/*.soundline`. Если сидер
уважает валидацию, helicopter в банк не попадёт: 9 рецептов вместо 10, и `retrieve`
по «helicopter»/«rotor» вернёт пустоту — то есть банк перестанет показывать, что умеет
отдавать зациклённые текстуры. Фазе 4 helicopter не нужен: тест восстановления слотов
делается на любом рецепте, и брать заведомо внеконтрактный в фикстуры не стоит.

Заодно проверено и зафиксировано, что для `loop`-звука хвост эффекта **считается**:
заявленная длительность зациклённого звука — это период петли, а буфер на 4046 мс
даёт цикл в 2.7 раза длиннее обещанного, то есть шов слышен.

### 6.3. Анализатор: отклонения от ТЗ

| Что | ТЗ | Сделано | Почему |
| --- | --- | --- | --- |
| метрика | один `profileDistance` = поля + STFT loss | `profileDistance` (поля), `stftDistance` (волны), `soundDistance` (оба, 50/50) | STFT loss невозможно посчитать из `SoundProfile`: профиль — 100 чисел, лоссу нужно аудио. При этом банк рецептов хранит только профили, и retrieve обязан сравнивать рецепты, ничего не рендеря. Одна функция не может обслужить оба вызова. |

FFT свой, radix-2, twiddle-факторы вращением, а не `Math.cos` на бабочку. `peakHz`
уточняется параболической интерполяцией по логарифмам: бин 512-го окна — 86 Гц, а
различать надо 1055 против 1098 (§9.2), то есть полбина. Проверено на синусах:
ошибка < 21 Гц на 1055/1098/3210 Гц.

Мини-FFT плейграунда (`apps/web/src/lib/fft.ts`) сознательно **не** переиспользован,
как и требовал §9.1.

### 6.4. Найден и исправлен баг детектора онсета — в анализаторе и в плейграунде

«Самый крутой подъём» искался с кадра 1. У звука, у которого все слои с
`attack 0ms`, подъёма нет вообще: сигнал начинается на полной амплитуде на сэмпле 0,
и каждый следующий кадр тише предыдущего. Максимальный «подъём» тогда равен нулю и
находится в хвостовой тишине, которую рендерер всегда дописывает, — онсет уезжает
за конец звука, а весь профиль обнуляется. Ни ошибки, ни предупреждения.

Исправлено в `packages/analyzer/src/profile.ts` (кадр 0 сравнивается с неявной
тишиной перед сигналом) и тем же однострочником в `apps/web/src/lib/analysis.ts`,
где была ровно та же формула, — иначе Compare-панель ломалась бы на любом рецепте
из одних `attack 0ms`. Регрессионный тест зафиксирован.

### 7.1. Отклонения от ТЗ

| Что | ТЗ | Сделано | Почему |
| --- | --- | --- | --- |
| кандидат | вектор пишется обратно **в AST** | вектор пишется в **текст**, затем `parse` | (а) Измеряется ровно то, что будет отгружено: рецепт пишется с точностью `roundLiteral`, и поиск по полным float'ам с округлением в самом конце отдал бы рецепт, который никто не рендерил. Округление на входе делает пространство поиска в точности множеством записываемых рецептов. (б) Парс — микросекунды против миллисекунд рендера. (в) Нет второго пути перезаписи дерева: пересборка `SoundAST` с подстановкой литералов — это все readonly-типы, и баг там даёт валидный на вид AST, говорящий не то, что текст. |
| подпись | `optimize(ast, targetProfile, renderFn, opts)` | `optimize({ source, target, render, ... })` | Кандидат — текст (см. выше), поэтому вход — текст. `target` — это `{ profile, signal? }`: с аудио fitness считается `soundDistance`, без него — только по полям профиля. Банк рецептов хранит профили и не хранит аудио, так что profile-only — нормальный режим, а не деградация. |
| fitness | `profileDistance(...)` | `soundDistance` + штрафы | Кандидат, не прошедший валидатор, **не рендерится вообще** (spec-first, fail fast) и получает штраф 4 — без градиента внутри невалидной области, чтобы поиск не ходил через неё. Клиппинг — штраф 2, упорядоченный по distance, то есть у него есть путь наружу. Это прямое требование §5.3/§11: у `explosion` запас ~2 дБ, и поиск, которому велено только совпасть по спектру, охотно его съест. Есть тест. |
| поиск | не оговорено | в единичном кубе, оси частот и времён логарифмические | На линейной оси `[500..8000]` Гц всё ниже 1 кГц занимает первые 7 % интервала, и равномерно засеянная популяция почти не попадает туда, где сосредоточена энергия большинства SFX. Кривая та же, что у слайдеров плейграунда. |

**Исправлен баг счётчика простоя (найден ревью, 2026-08-05).** Флаг «был прогресс»
ставился внутри ветки принятия кандидата по условию `score < scores[bestIndex]`. Когда
заменяемый кандидат — сам текущий лидер, его счёт к этому моменту уже перезаписан, и
условие читается как `score < score`, то есть ложь. Лучший фитнес падал поколение за
поколением, счётчик простоя при этом рос, и прогон объявлялся «stalled» посреди
сходимости. Замерено до правки: 8 из 60 засеянных 6-мерных прогонов остановились так,
один — улучшившись за два поколения до сдачи. Это ровно то дорогое направление ошибки,
против которого и калибровался порог: ложный «stalled» отправляет LLM переделывать
топологию. Теперь прогресс определяется сравнением лучшего фитнеса до и после поколения.
Регрессионный тест проверяет инвариант на восьми сидах, а не на одном удачном: если
прогон остановился по простою, последние `stallGenerations` отчётов обязаны показывать
один и тот же лучший фитнес.

`stallGenerations` = 20 (треть бюджета), а не 12: замерено на 3-мерном Растригине —
порог 12 останавливал поиск на вдвое большей ошибке, чем тот же прогон, которому
позволили продолжить. Плато в десяток поколений — рядовая середина поиска, а не
вердикт. Цена ошибки асимметрична: ложный «stalled» отправляет LLM переделывать
топологию, которую переделывать не надо.

`roundLiteral` вынесен в `@txt2sfx/core` (`grammar/units.ts`) и используется и
оптимизатором, и слайдерами плейграунда: два приватных экземпляра этой таблицы
рано или поздно разошлись бы в том, как пишется одно и то же число.

### 7.2. Найден баг: `getChannelData` отдаёт представление в нативной памяти

Первый прогон сквозных тестов **убил воркер vitest** без JS-стека, а до этого
`stftDistance` начал возвращать NaN на сигналах, в которых за мгновение до этого
не было ни одного нечисла.

Причина: `node-web-audio-api` возвращает из `getChannelData(0)` вид на память,
которой владеет нативный контекст. Оптимизатор держит `target.signal` живым через
сотни рендеров; контексты этих рендеров становятся недостижимы, GC их собирает — и
освобождает буфер под видом, который всё ещё держит цель. Сэмплы превращаются в NaN,
любая метрика с этой целью становится NaN (а `NaN <= x` — ложь, поэтому DE не
принимает ни одного кандидата и «лучшим» остаётся seed), затем процесс падает.

Исправлено копированием на выходе из аудиостека — `Float32Array.from(...)` — в
хелперах тестов оптимизатора и анализатора. **Важно для фазы 5:** `seed.ts` рендерит
десять рецептов и снимает профили, то есть окажется ровно в этой же позиции. Всё, что
держит сэмплы дольше контекста, обязано копировать.

### 8.2. helicopter в банке: решение принято в пользу «загружать и сообщать»

Дедлайн из §6.2 наступил здесь. Сидер валидирует каждый рецепт и **загружает всё**, печатая:

```
seeded 10 of 10 recipes
  stored  helicopter — error duration.contract
  stored  sword-clash — warn duration.contract

1 recipe(s) carry validation errors: helicopter.
They were stored anyway — ... Re-run with --strict to refuse them instead.
```

Почему так: отказ оставил бы банк без единственной зациклённой текстуры, и
`GET /api/retrieve?prompt=helicopter rotor loop` отвечал бы пустотой — тихая дыра в
демонстрации вместо видимого изъяна в одном рецепте. Флаг `--strict` переключает на
отказ (9 из 10) и выставляет ненулевой exit code; это режим для CI, когда находка из
§6.2 будет закрыта в ту или другую сторону. Оба режима под тестами.

**Решение заказчика (2026-08-05): отложено до конца работ.** Формулировка: «не знаю
пока, думаю уже когда всё будет готово можно решить. Может вообще придётся переделать.
Можно ослабить требования к рецептам».

Значит, на столе три варианта, и третий появился только сейчас:

1. переделать DSP ротора (`feedback ≤ 0.65`) — другой звук;
2. поднять `CATEGORY_LIMITS.cycle.maxDurationMs` до ~4500 и заголовок до 4046;
3. **ослабить сам инвариант** — например, сделать `duration.contract` предупреждением
   для `loop`-звуков, или поднять порог error с 25 % выше.

Третий вариант надо оценивать вместе с фазой 7: если бенчмарк покажет, что модель
регулярно натыкается на этот же инвариант на честных рецептах, требование слишком
строгое, и это довод сильнее любых рассуждений про один helicopter. До тех пор всё
работает: сидер грузит и сообщает, `--strict` отказывает, оба режима под тестами.
Текущая цена ясна и зафиксирована: банк содержит рецепт, который `POST /api/recipes`
не принял бы.

### 8.3. `GET /api/llms.txt` — точка входа для внешнего агента

11.9 КБ текста, **сгенерированного из тех же таблиц, которыми пользуются парсер и
валидатор**: `PRIMITIVES`, `EFFECTS`, `ENVELOPE`, `CATEGORY_LIMITS`, `GLOBAL_LIMITS`.
Написанный руками документ был бы верен в день написания и тихо неверен фазу спустя;
этот не может описать примитив, которого нет, или пропустить параметр, который есть.
Тесты проверяют, что упомянуты все 8 примитивов, все 6 эффектов и все 9 категорий с
их числами.

Содержимое: два правила, экономящие больше всего итераций (не починять сгенерированный
JS; писать `~value[min..max]` для всякого неуверенного числа), грамматика, таблицы
параметров с единицами/диапазонами/дефолтами, таблица категорий как контракт, список
глобальных инвариантов, honesty about limits, few-shot из банка и описание API.

Прочее по требованию §0: CORS открыт (`origin: true`) — банк публичный, секретов нет,
а закрывать его политикой одного источника значило бы заблокировать единственный
сценарий; 404 на неизвестный маршрут отсылает к `/api/llms.txt`; каждая ошибка несёт
машинный `error` и человеческий `message`, а отвергнутый soundline — ещё и `issues` с
их `hint`.

Ранжирование `retrieve`: FTS5 + bm25 с весами по колонкам (`name` 5, `tags` 3,
`prompt` 1). Промпт превращается в выражение с **`OR`**, а не с дефолтным неявным `AND`
(ни один рецепт не содержит сразу «coin», «pickup» и «sound»), и каждый токен
**закавычивается** — промпт это пользовательский текст, а `NEAR`, `OR` и `*` в FTS5
операторы, так что без кавычек поиск «near miss» это 500. Пустой ответ заменяется
фолбэком по рейтингу с флагом `fallback: true`: вызывающему нужны примеры грамматики,
и взять их больше негде, но принять фолбэк за ответ по промпту он не должен.

### 8.4. Обход бага инструментов: `node:sqlite` под Vite

`import { DatabaseSync } from 'node:sqlite'` корректен и работает, когда файл запускает
Node, но падает под Vite (то есть в тестах): Vite определяет встроенные модули, срезая
префикс `node:` и глядя имя в `module.builtinModules`, — а `sqlite`, пока он
экспериментальный, есть в этом списке **только под префиксом**. Vite заключает, что
существует npm-пакет `sqlite`, переписывает импорт на него и не может его найти.
`server.deps.external` не помогает: к моменту externalize префикс уже срезан, и Node
получает специфаер `sqlite`.

Решение — `process.getBuiltinModule('node:sqlite')` в `db.ts`: это штатный API ровно для
такой ситуации (достать встроенный модуль без специфаера, который бандлер может
переписать), production и тесты грузят один модуль одной строкой. Тип импортируется
обычным `import type` — типовые импорты стираются.

Апстрим это починили в **vitest 3** ([PR #7179](https://github.com/vitest-dev/vitest/pull/7179),
закрывает issue именно про `node:sqlite`); воркспейс на vitest 2.1.9. После бампа
обходной путь можно убрать и вернуть обычный импорт — это решение фазы 7 вместе с CI,
потому что мажорный бамп тестового раннера трогает все 462 теста.

Ещё одна мелочь того же рода: Node не отображает `.js` в импортах на `.ts`, поэтому
`node src/seed.ts` не работает при `verbatimModuleSyntax`-стиле импортов. Скрипты `dev`
и `seed` собирают проект и запускают `dist/`.

### 8.5. FTS5 — это флаг сборки Node, и Node его переключал

Самая ценная находка ревью. JS-API `node:sqlite` стабилен, но собран ли его SQLite с
FTS5 — **нет**: флага нет в Node 22.5–22.15, он появляется в 22.16, снова отсутствует
во **всех** 23.x и включён безусловно с 24.0. То есть «есть `node:sqlite`» не значит
«эта схема запустится», а падение выглядит как голое `no such module: fts5` из
`CREATE VIRTUAL TABLE` в глубине старта — читается как битая схема, а не как отсутствующий
флаг сборки.

Что сделано:

- `engines` исправлен с неверного `>=22.5.0` на `>=22.16.0 <23 || >=24.0.0`;
- `openBank` пробует FTS5 в `temp`-таблице до применения схемы и падает с внятным
  текстом, называющим версию Node и диапазон, — проверка в рантайме надёжнее любой
  строки в `engines`, которая всё равно носит совещательный характер;
- `--experimental-sqlite` убран из трёх скриптов: он нужен только на 22.5–22.12, где
  FTS5 всё равно нет, а на будущих версиях удалённый флаг превратился бы в фатальное
  «bad option». Проверено: на Node 24.15 сервер стартует без флага и **без всякого
  ExperimentalWarning** — прежняя запись про предупреждение тоже была устаревшей.

Заодно перепроверено утверждение про better-sqlite3: с v13 (июль 2026) он кладёт
N-API-прибилды прямо в свой tarball, включая `prebuilds/win32-arm64.node`, без
install-скрипта. То есть возражение «нужен тулчейн» к нему больше не применимо, и это
готовый путь отхода, если `node:sqlite` когда-нибудь отрегрессирует. Решение не меняется
— ноль зависимостей против одной на 17 МБ, — но записано в TSDoc `db.ts`.

### 9.1. Фаза 6a — локальный плейграунд (готово, вынесен вперёд фаз 3–5)

Причина переноса: без интерактивного прослушивания качество примеров не доводится, а
работа через файлы и ручной рендер в WAV — слишком долгий цикл. Промпт-бар и поле
Gemini-ключа осознанно **не** сделаны: они требуют `packages/agent` (фаза 7) и валидатора
(фаза 3), без которого LLM будет уверенно выдавать нерабочий soundline. Всё остальное из
§9 закрыто, и это ровно та часть, которой не нужен ключ.

**Файлы:** `apps/web/` — `index.html`, `vite.config.ts`, `plugins/examples-fs.ts`,
`src/{main.tsx,App.tsx,styles.css}`, `src/lib/{examples,slots,engine,fft,highlight}.ts`,
`src/components/{Editor,Diagnostics,Gallery,Sliders,Timeline,Visualizer,ExportPanel}.tsx`.
Vite 5 + React 19 + TS, алиасы на `src/index.ts` пакетов (как в `vitest.config.ts`).

Ключевые решения, которые не стоит переоткрывать:

- **Источник истины — текст в редакторе.** Слайдеры не мутируют AST, а перезаписывают
  спан `NumberLiteral.loc` в исходнике. Важно: этот `loc` покрывает только числовой токен
  (`3200Hz`), без `~` и `[500..8000]`, поэтому рамка слота остаётся на месте, а редактор
  всегда показывает то, что звучит. После каждой правки офсеты сдвигаются — значит
  переспарсить и пересобрать список слотов до следующего изменения.
- **Два пути воспроизведения.** Play — живой граф через `buildGraph` (тот же путь, что у
  экспортируемого кода); Loop — офлайн-рендер через зацикленный `AudioBufferSourceNode`,
  потому что `cycle`-звук иначе не оценить, а зацикливание живого графа даёт шов на стыке.
- **Картинки рисуются по офлайн-рендеру, не по `AnalyserNode`** — изображение соответствует
  рецепту, а не моменту, и есть до нажатия Play.
- **Ось частот логарифмическая**, слайдеры частот и времён — тоже (`lib/slots.ts`):
  на линейной шкале `[500..8000]` вся полезная нижняя часть умещается в 5 % хода.
- **Запись в `examples/` только в dev** (`apply: 'serve'`, имя строго `[a-z0-9-]+`,
  каталог только `examples/`, перевод CRLF→LF из-за `.gitattributes`). Список рецептов в
  dev берётся с этого же эндпоинта, а не из `import.meta.glob`: glob — снапшот времени
  сборки и не видит только что сохранённый файл. HMR для glob-модуля намеренно
  проглатывается (`import.meta.hot.accept`), иначе Save вызывает full reload и убивает
  несохранённые буферы.
- **Save под другим именем = «сохранить копию»**: буфер исходного рецепта остаётся
  грязным, ничего не теряется молча.

### 9.2. `bubble-pop` переписан под референс

Заказчик указал эталон — `C:\Projects\games\block_chpok\src\pop1.mp3` (игровой хлопок

каверны растёт по мере схлопывания), спад ≈1.2 дБ/мс, энергия сосредоточена в 0.8–2 кГц.

(43 мс) — артефакт. Окно накрывало весь хлопок и смазало один скользящий тон в три
пика. С окном 512 картина однозначна. **Для транзиентов измерять коротким окном.**

### 9.3. Compare view — сравнение с референсом в плейграунде

**Файлы:** `src/components/Compare.tsx`, `src/lib/{analysis,draw}.ts`, `spectrumAt` в
`src/lib/fft.ts`. Референс загружается через file-picker или drop, декодируется в
браузере, живёт **только в памяти вкладки** — файл пользователя никуда не копируется.

Решения, без которых панель была бы бесполезной:

- **Выравнивание по онсету включено по умолчанию.** Записанный референс начинается
  когда включили запись, а не когда случился звук: в эталонном `pop1.mp3` хлопок стоит
  на 125 мс за тихим пре-роллом. Без выравнивания diff показывает картину сдвига, а не
  разницу звуков. Онсет ищется как **максимальный подъём** 1-мс RMS-огибающей, потом
  откат к «подножию» транзиента и уточнение до сэмпла. Порогом искать нельзя — порог
  цепляется за пре-ролл и выравнивает два звука по шуму комнаты.
- **Нормировка пиков тоже по умолчанию.** Референс 0.98 против рендера 0.79 — это
  постоянные 1.8 дБ по всему полю, они топят спектральную разницу, которая и нужна.
- **Декодирование в `OfflineAudioContext` на `GLOBAL_LIMITS.sampleRate`.** Платформа
  сама пересемплирует 48 кГц референс к 44.1 кГц рендера, и спектрограммы можно вычитать
  бин к бину. Иначе сетки бинов не совпадают.
- **Три режима:** `stacked` (кандидат над референсом), `overlay` (огибающие в одной
  панели — там наложение реально помогает) и `diff` (знаковая разница, расходящаяся
  палитра). Палитра diff — циан/янтарь, а не красный/зелёный: картинку должен уметь
  прочитать любой читатель, включая дальтоника и vision-модель.
- **Переключатель окна `full` / `zoom`.** Хвост комнаты у референса длиннее кандидата в
  5 раз и на общей оси сжимает исследуемые первые 40 мс в полоску у левого края.
- **Канвас самодостаточен:** в шапке имена обоих сигналов, режим и состояние
  выравнивания/нормировки, в diff — легенда направления. Картинка, которую нельзя
  прочитать без окружающего UI, бесполезна ровно в тот момент, когда её скопировали.
  `Copy PNG` / `Save PNG` дают 1761×579 (~70 КБ), `Copy numbers` — markdown-таблицу
  метрик; для vision-модели полезно отдать и то и другое.
- Метрики считаются в окне **512 сэмплов (~12 мс)** у собственного онсета каждого
  сигнала — см. предупреждение из §9.2 про смазывание длинным окном.

Сверка с офлайн-замерами сошлась: панель находит онсет референса на 124.7 мс (вручную
было 125) и даёт спад 0/−3/−9/−17/−21/−30 дБ (вручную 0/−2.8/−9.1/−16.6/−20.7/−30.0).

`lib/draw.ts` — общий слой рисования для `Visualizer` и `Compare`: палитра, лог-ось,
осциллограмма. Иначе суждение, сложившееся в одной панели, не переносится в другую, а
это и есть смысл сравнения.

### 14.2. Провайдеры на `fetch`, а не на SDK

Оба провайдера — сырой HTTP через `fetch`, без вендорских SDK. Решают два требования:
пакеты несут **ноль runtime-зависимостей** (§4), и плейграунд должен работать с ключом,
который пользователь вставил в браузере, — значит один и тот же код провайдера
исполняется в Node и на странице, и каждый его байт уезжает в бандл. SDK на вендора —
это два дерева зависимостей и проблема бандлинга ради десятка строк `fetch`.

Цена названа честно в TSDoc: ретраи, отображение ошибок и формы ответов теперь наши, и
изменение формата на стороне вендора ломает нас там, где бамп SDK бы починил. Поэтому
каждая форма запроса задокументирована с версией API, под которую написана, а политика
ретраев живёт в одном месте (`providerFetch`).

Детали, которые не вкусовые:

- Anthropic: **не отправляются** `temperature`/`top_p`/`top_k` и никакой `thinking` —
  на текущем семействе моделей это 400, а не «менее случайные ответы». Есть тест,
  падающий, если кто-то вернёт их обратно. `stop_reason: 'refusal'` приходит **успешным**
  200 с пустым `content`, поэтому проверяется до чтения текста; `max_tokens` —
  ошибка, а не рецепт, потому что половина рецепта парсится до половины слоя и падает.
- Gemini: ключ в заголовке `x-goog-api-key`, **никогда** в query string — ключ в URL
  оседает в логах прокси, истории браузера и `Referer`, а он чужой.
- mock: кончился сценарий — исключение, а не цикл по кругу. Цикличный mock превращает
  баг цикла в бесконечный разговор, который выглядит как «медленно».
- Ни один провайдер не читает ключ из окружения сам: плейграунд держит вставленный ключ
  в памяти вкладки и передаёт вызовом, а провайдер, тихо падающий на `process.env`,
  использовал бы неверный ключ ровно тогда, когда они расходятся.

### 14.3. Few-shot: предпочтение проходящих валидацию (решение заказчика)

`selectFewShot(recipes, k)`: набирать примеры из рецептов, проходящих валидацию;
**меньше примеров лучше, чем пример, который конвейер отверг бы.** Откат на невалидные
— только если чистых нет вовсе (промпт без примеров не учит форме языка), и тогда рядом
называется правило, которое каждый из них ломает, чтобы модель копировала структуру, а
не дефект.

Применяется в двух местах: в системном промпте агента и в `GET /api/llms.txt`, где
роут запрашивает вдвое больше рецептов и фильтрует. Так защита достаётся и чужому
агенту, а не только нашему циклу.

Что это даёт помимо ответа ревью: вопрос «что делать с `helicopter`» перестал быть
блокирующим. Починят рецепт, ослабят инвариант или не сделают ни того ни другого —
агент всё равно не учится на примере, который конвейер отвергает. Тест
`fewshot.test.ts` начинается с проверки предпосылки: если `helicopter` когда-нибудь
станет валидным, тест скажет об этом, а не будет молча проверять пустоту.

### 14.4. Жёсткое правило и второй случай «упёрся»

ТЗ: LLM меняет топологию, только если оптимизатор упёрся. Реализовано, и по ходу
нашёлся второй, не менее законный случай — **рецепт без единого `~`-слота**. Фитить
нечего, значит расстояние, на котором он рендерится, и есть расстояние этой структуры,
и менять остаётся только структуру. Это к тому же частый вывод модели: первая попытка
охотно пишет уверенные литералы.

Важно: по `de` этого не прочитать. При `dimensions === 0` оптимизатор возвращает
`stopped: 'target'` — «оптимизировать нечего», а не «порог достигнут». Поэтому в цикле
`stuck = de.stopped === 'stalled' || slots.length === 0`, с комментарием.

Обратная сторона правила тоже реализована: если поиск **всё ещё улучшался** и просто
исчерпал бюджет поколений, цикл заканчивается с `outcome: 'distance'` и не тратит
итерацию модели. Просить новую топологию там — значит выбросить работающий поиск; это
та же асимметрия, из-за которой `stallGenerations` = 20, а не 12 (§7.1).

### 14.5. Мелкие находки фазы

- **Отказ модели — это ответ.** Ответ без единого ограждения кода завершает прогон с
  `outcome: 'refused'` и текстом модели в `message`. Контракт сам велит отказываться от
  голоса и правдоподобных животных одним предложением; требовать в ответ на это
  «пришли fenced block» — значит выпросить ровно тот разочаровывающий звук, против
  которого инструкция и написана. Ответ *с* ограждением, но без рецепта — другое дело,
  он ремонтируется.
- **Извлечение рецепта не берёт fenced-блок без заголовка.** Соблазнительное «ну возьми
  тогда последний блок» читает JS-сниппет как рецепт и превращает честное «ты не прислал
  soundline» в ошибку парсинга чужого `play(ctx, 0)`: одна потраченная итерация и
  путаница в транскрипте. Найдено тестом, исправлено в `prompts.ts`.
- **Запрос — это значение, а не живой массив.** Цикл передавал провайдеру тот же
  мутируемый `messages`, который потом дополнял; mock записывал ссылку, и «транскрипт»
  первого вызова показывал последний ответ. Теперь передаётся копия — заодно это
  корректно для любого провайдера, который очередь или ретрай делает сам.
- **`param.slot-range` поймал сам себя на цели bench:** слот `click ~1ms[0.5..6]` вышел
  за задокументированный предел `width` (5 мс) — правило сработало на нашем же
  материале, диапазон исправлен. Второй warn (`envelope.attack-longer-than-voice`) снят
  добавлением `attack 0ms` — той самой идиомы, которой контракт учит модель для щелчков.
- **Устаревшие числа в плане** (см. §11): `bubble-pop` — 876 Б и пик 0.785. Замеры
  пересняты для всех десяти рецептов и лежат в `docs/PRIMITIVES.md`.

Шесть целей, скриптованная модель, profile-only метрика, оптимизатор 16 × 24, seed 1,

статистику даст v0.3 с пятьюдесятью.

### 15.1. Галерея: банк **рядом с** `examples/`, а не вместо

Единственное существенное отклонение от формулировки §9/§12. ТЗ говорило «галерея из банка
**вместо** `examples/`»; сделан переключатель источника.

Причина не в осторожности, а в том, что эти два хранилища делают разное. `examples/`
пишется под `vite dev` (§9.1) — это место, где рецепт **авторится**, и именно там лежит
референсный набор репозитория, на который опираются тесты и документация. Банк —
общий, поисковый, источник few-shot для агента; туда рецепт **публикуется**. Замена
первого вторым: (а) выключила бы Save и осмысленную работу без запущенного сервера,
(б) сделала бы галерею пустой в статической сборке, (в) в момент, когда сервера нет,
оставила бы плейграунд вообще без рецептов — а mock-провайдер отвечает именно из них.

Третий источник появился по ходу и оказался нужен: `session` — рецепты, сгенерированные
только что и не сохранённые никуда. Они идут первыми и перекрывают одноимённые
хранимые (`lib/catalog.ts`): две строки с одним именем выбирали бы один и тот же буфер
редактора и отличались бы только значком. Группы в сайдбаре подписаны, потому что
разница между ними — не происхождение, а что с рецептом можно сделать: session не
сохранён, `examples/` пишется, банк опубликован.

### 15.6. Мост в devtools и три дефекта, которые он нашёл (2026-08-05)

Заказчик получил на Gemini плохой результат («звук барабана между бочкой и snare» на
промпт про камень в озере) и предложил: пусть на этапе доработки в роли LLM выступает
внешний агент через devtools. Сделано — `apps/web/src/lib/bridge.ts` плюс
`window.txt2sfx` (только под `vite dev`, в статическую сборку не попадает, есть тест).
Провайдер `bridge` парковает запрос, отвечающий пишет рецепт руками, а всё ниже —
извлечение, валидатор, рендер, оптимизатор, фидбек — работает без изменений. Плюс
`measure()`: профиль кандидата и цели, замечания валидатора, расстояние и **те самые
директивы `humanReadableDiff`**, которые цикл отправил бы модели.

Мотив не в удобстве: подстройка цикла против хостед-модели — медленный и шумный
эксперимент, где каждое изменение стоит round trip и новой выборки, так что два прогона
никогда не расходятся по одной причине. Мост убирает и сеть, и сэмплирование: проверяется
**наша** половина.

Первый же прогон нашёл три дефекта, из которых модель виновата в одном:

1. **Окно простоя больше бюджета поколений — ветка «переделай топологию» недостижима.**
   `stallGenerations` был константой 20 (треть от дефолтных 60), а плейграунд я поставил
   на 14 поколений, чтобы браузер не подвисал. `stopped` мог быть только `target` или
   `budget`, а `budget` цикл сознательно не считает поводом просить новую структуру (§14.4).
   Итог: модель ни разу не увидела директивы диффа. Исправлено — `stallWindowFor(generations)`
   в `de.ts` (треть бюджета, не меньше 6; для дефолтных 60 это те же измеренные 20),
   регрессионный тест на инвариант «окно всегда меньше бюджета».
2. **Бюджет итераций съедается ремонтом.** `maxIterations: 3`, из них две ушли на parse
   error и нарушение инварианта, третья — первый и последний замер. Поднято до 5;
   ремонтные итерации ничего не рендерят и стоят дёшево.
3. **`measure()` возвращал прошлый рендер.** API собирался из значений замыкания, и
   вызов сразу после прогона отдавал числа предыдущего рецепта — я на них едва не сделал
   вывод. Теперь всё изменяемое читается через ref, объект на `window` ставится один раз.

Добавлено по ходу: событие `generation` в `AgentEvent` (фит — самое медленное место цикла,
44 поколения без единой строки прогресса читаются как зависание) и **кнопка «Fit to
reference»** в панели Slots — 60 поколений по текущему буферу. Она отвечает на «поиск
всё ещё улучшался, когда кончился бюджет»: по логике самого цикла ответ в этом случае —
больше поколений, а не новый вызов модели. Каталог `.refs/` добавлен в `.gitignore`:
референсные записи — чужое аудио под чужой лицензией, в репозиторий они не попадают,
а `vite dev` их отдаёт по `/@fs/`.

**Что показал прогон по воде** (цель — `404829__nilbul__water-splash.wav`, профиль:
`noiseRatio 0.939`, `flatness 0.575`, центроид 8 кГц → 6.6 кГц, 796 мс):

| попытка | расстояние | что изменилось |
| --- | --- | --- |
| Gemini | 0.556 → **0.509** (budget) | `sub 180→45Hz` + `modal membrane Q15` = буквально бочка и корпус барабана |
| мост, 1 | 0.474 → **0.457** (budget) | ни одного осциллятора, только шум в полосах — по замеру, а не по слову «камень» |
| мост, 2 | 0.473 → **0.428** (budget) | по диффу: огибающая цели двугорбая, поэтому медленная атака + `delay` на поздних слоях |
| мост, 3 | 0.287 → **0.278** (budget) | полоса на 600 Гц вместо lp (доминанта уехала на 82 Гц), шире полосы, живой хвост |
| + Fit | 0.278 → **0.278 (stalled)** | числа исчерпаны: остаток ошибки — структурный |

Ключевое наблюдение — не числа, а то, **чем** они получены: цель измеряется в 0.94 по
noiseRatio, то есть это широкополосный шум, и любой тональный слой в рецепте — ошибка,
которую оптимизатор исправить не может. Gemini написал два тональных слоя, потому что
слово «камень» тянет к удару, а измерение говорит обратное. Директивы диффа это и
сообщают; их просто никто не показал модели (дефект 1).

Второе наблюдение — про грамматику. Огибающая цели `[1, 0.04, 0.09, 0.18, 0.13, 0.06,
0.04, 0.05]` — это удар, пауза, **второй подъём** и длинное плато. Двугорбость выражается
уже сейчас (медленная атака + `delay`), плато — через `hold`, и это недоиспользованный
инструмент. А вот чего в наборе нет физически: **плотного поля мелких событий**. У воды,
гравия, дождя и огня спектрограмма зернистая, а `noise` стационарен, а `chirp` — один
свип. Отсюда заявка на примитив `grains` (N коротких событий в окне: плотность, разброс
частоты и времени, seed) — он процедурный, в экспорте это один буфер, и открывает сразу
целый класс. Пока его нет, `flatness` упирается в ~0.42 против нужных 0.575.

Третье, дешёвое и не сделанное: **слоты, упёршиеся в границы своего диапазона, никому не
сообщаются.** У Gemini таких было 6 из 8, у моего третьего прохода — 3 из 4
(`bp ~3000Hz[400..3000]`, `lp ~1400Hz[100..1400]`). Это DE говорит «оптимум снаружи того,
что ты мне разрешил» — сигнал, который стоит добавить и в `OptimizeResult`, и в
repair-сообщение.

### 15.7. Примитив `grains`, нормализация промпта, ключ в secure storage (2026-08-05)

Три задачи по итогам §15.6. **616/616 тестов**, все typecheck-и чистые, `vite build`
341 КБ / 113 КБ gzip.

**1. `grains` — девятый примитив.** `packages/core/src/primitives/grains.ts`, генератор в
`compile/buffers.ts` (две половины, TS и строка для экспорта), сигнатура в
`grammar/signatures.ts`, 8 тестов в `test/grains.test.ts`.

Одно зерно — затухающая синусоида с подъёмом частоты на 6 % за свою длину: модель
Миннарта, та же физика, что в `bubble-pop` (§9.2). Параметры: `freq`, `rate`
(зёрен в секунду), `width`, `spread` (разброс в октавах), `jitter` (0 — метроном,
1 — естественный разброс). Решения, которые стоит знать:

- **Плотность — не громкость.** Поле нормируется к пику 1, поэтому `rate 220` плотнее
  `rate 12` (RMS 0.0442 против 0.0218) и не громче (пик 0.477 против 0.545). Иначе
  модель, потянувшись к плотности, каждый раз перекручивала бы `gain` — та самая
  путаница, из-за которой водные попытки звучали неверно. Аналитической границы у суммы
  перекрывающихся зёрен нет, поэтому, в отличие от `modal`, нормировка идёт вторым
  проходом (~40 байт в экспорте).
- **Порядок операций в двух половинах совпадает буквально.** `f * (i/R)` и `f * i / R`
  различаются в последнем бите, а тест паритета требует побитового равенства живого
  графа и экспорта. Комментарий в коде стоит там же, где ловушка.
- **Цена: ~960 Б на однослойный рецепт.** Та же сделка, что в §5.4: процедурные
  генераторы — фиксированная стоимость отказа от ассетов.

**Проверка на воде дала честный, но неудобный результат.** Четвёртая попытка (два
слоя из четырёх — грани) дала 0.424 → **0.322**, то есть *хуже* ручной шумовой версии
(0.278), а `flatness` осталась 0.401 против 0.435. Вывод, который из этого следует, —
не «примитив не нужен», а **метрика не видит того, что он добавляет**: «поле мелких
событий» — свойство *временнóе* (плотность транзиентов), а в `SoundProfile` нет ни
одного поля, которое его измеряет; STFT-лосс задевает это лишь косвенно. То есть
оптимизатор не может вознаградить гранулярность, даже когда она перцептивно верна.
Отсюда следующая заявка, уже обоснованная данными: **поле плотности транзиентов в
профиле** (например, crest factor по коротким окнам или число онсетов в секунду).
До тех пор судить о `grains` можно только на слух — что плейграунд и позволяет.

**Открытое расхождение, не разобранное:** после того прогона `Fit` сообщил
`0.278 → 0.278 (stalled)`, а панель на том же буфере показывала 0.322. Два пути,
которые должны считать одно и то же (`optimize` и `measure`), дали разные числа.
Это подрывает любое сравнение, поэтому это первое, что надо проверить; гипотезы —
разный сид рендера, разная длина буфера или устаревшее замыкание в одном из путей.

**2. Нормализация промпта.** `packages/agent/src/query.ts`: `searchQuery` — один
дешёвый вызов (`maxTokens: 64`), запрос → 3–8 английских ключевых слов; `parseKeywords`
отдельно и строго — прозу отвергает, а не подрезает, потому что у вызывающего есть
хороший фолбэк. В цикле — `rewriteQuery?: boolean` (по умолчанию выключено; включено в
плейграунде для всех провайдеров кроме mock) и `retrievalQuery?: string`, который его
перебивает. Новое событие `retrieval` показывает, чем искали и что нашлось, включая
флаг `fallback`: три примера, не совпавших ни с чем, выглядят точно как три совпавших,
и это самый дорогой тихий отказ в цикле. Рерайт не делается, когда банка нет — вызов
без потребителя. 15 тестов.

**3. Ключ в secure storage.** `apps/web/src/lib/keystore.ts`: AES-GCM, ключ шифрования —
**неизвлекаемый** `CryptoKey` (`extractable: false`) в IndexedDB, шифротекст рядом.
`localStorage` не используется: он хранит открытый текст, и правило §4 остаётся в силе.
Опция per-provider (чекбокс `remember`), сохранение — в момент реального использования
ключа, а не на каждое нажатие клавиши, и кнопка `forget` рядом.

Честная формулировка, вынесенная в TSDoc: **это не сейф**. Страница, которая ключом
пользуется, обязана уметь его прочитать, поэтому скрипт, попавший на этот origin,
вызовет `load()` так же, как приложение. Что даёт эта схема: на диске нет читаемого
текста (в DevTools → Application видны IV и шифротекст), ключ шифрования нельзя
выгрузить даже нашим собственным кодом, и копия базы на другой машине бесполезна.
Отсюда и opt-in, и `forget`. 8 тестов на настоящем WebCrypto против in-memory KV;
последний проверяет саму гарантию — в хранилище нет секрета, а `exportKey` на
wrapping-ключе падает.

### 15.8. `bend`, затенённая переменная и расхождение метрики со слухом

Заказчик послушал поле зёрен: «звук стал богаче и интереснее», но «больше похоже на
разлёт мелких осколков льда», а в референсе — всплеск воды. Отчёт точный и указал на
физику: лёд и стекло — это короткий яркий пинг, **частота которого не двигается**, а
вода — пинг с восходящим глиссандо (каверна схлопывается, резонанс растёт). Подъём был
зашит константой 6 % — почти не слышно.

**Найден настоящий баг, попутно.** Фактор подъёма назывался `k`, а цикл по зёрнам
считает индексом `k` — переменная была затенена, поэтому `bend` не действовал вообще, а
чирп зависел от **номера зерна**. Ошибка была одинаковой в обеих половинах генератора,
поэтому тест паритета остался зелёным: паритет доказывает, что два проигрывателя
согласны, а не что хоть один из них прав. Это записано комментарием там же, в
`buffers.ts`.

**`bend` стал параметром** (`0.25..4`, дефолт 1.3): `1` — лёд/стекло, `1.2–1.6` — вода,
меньше 1 — «блуп» поднимающегося пузыря. Означает **конечную** частоту зерна; внутри
делится на 2, потому что фаза `2πf·t·(1 + k·t/T)` даёт мгновенную частоту
`f·(1 + 2k·t/T)`, и параметр, который гнёт вдвое сильнее обещанного, хуже, чем никакого.
Тест проверяет и направление, и то, что `bend 1` действительно оставляет высоту в покое.

**Главная находка — метрика и слух расходятся, и расхождение измеримо.** Пятый проход
(зёрна ниже, длиннее, с подъёмом 1.45–1.6) дал 0.453 → 0.324, но оптимизатор при этом
утащил **6 из 8** слотов зёрен на верхнюю границу: freq 3948 из 4000, rate 294 из 300,
spread 3.44 из 3.5, bend 2.3 из 2.4. То есть поиск тянет звук ровно туда, откуда его
увёл слух — к ярким плотным пингам. Причина понятна: единственный способ поднять
`flatness` до референсных 0.575 нашими примитивами — сделать пинги ярче и плотнее, тогда
как настоящий референс берёт flatness широкополосной турбулентностью. Поля, измеряющего
«плотность мелких событий», в профиле нет, поэтому объяснить поиску разницу нечем.

Отсюда практическое правило, которое стоит перенести в документацию грамматики:
**`~слот` — это делегирование метрике.** То, что выбрано на слух, надо оставлять
литералом, иначе оптимизатор это перекрутит; в рецепте `stone splash` характер зёрен
записан числами, а слоты оставлены только там, где метрике можно доверять (частоты
фильтров и уровни).

**Второй отчёт слухом: «морская волна или песок из железного кузова».** Это
непрерывность, и виноваты были три вещи, все — про время, а не про спектр: слой `wash`
(полоса шума с `hold 220ms`) — буквально прибой; `rate 120` с 420-мс спадом — поток
капель, а не всплеск; мягкая атака вместо жёсткой кромки (у референса спад −8 дБ за
первые 5 мс, у кандидата было −1). Дальше — короткая серия проходов по слуху и по
огибающей, и каждый нашёл ровно одну ошибку:

| проход | что изменено | что сказал замер |
| --- | --- | --- |
| 6 | убран `wash`, `rate` 120→70, спады вдвое, `click` на кромку | пересол: `rate 14` дал шесть отдельных пингов, flatness 0.028 — почти чистые тоны, в огибающей дыры |
| 7 | аэрация вернулась как широкополосный слой на низком gain с длинным спадом и **без** `hold` | форма пошла в цель, но всплеск громче удара |
| 8 | всплеск и капли позже (пауза после удара), хвост длиннее, общий уровень +6 дБ | огибающая `[1, 0.96, ...]` — всплеск почти равен удару, а у референса там 0.04 |
| 9 | всплеск и капли тише (0.26/0.22) и позже (150/260 мс), аэрация тоньше | `[1, 0.19, 0.48, 0.17, 0.16, …]` против `[1, 0.04, 0.09, 0.18, 0.13, …]`: удар → пауза → всплеск → оседание. 802 мс против 796, noiseRatio 0.978 против 0.939, distance 0.333 |

Методический вывод из этой серии важнее самого рецепта: **каждый отчёт слухом находил
временнýю ошибку, которую метрика не подсвечивала**, а из шести директив диффа полезной
раз за разом оказывалась только одна — «energy sits too early». Метрика описывает спектр
подробно и время бедно, и именно поэтому она проигрывает уху на этом классе звуков.

И приоритет для следующего шага теперь не спорный: **поле плотности транзиентов в
`SoundProfile`** (crest factor по коротким окнам либо число онсетов в секунду) —
без него `grains` работает вслепую, а fitness активно вредит. Второе — расхождение
0.278/0.322 из §15.7.

### 15.9. Что осталось за пределами v0

Ничего из плана. Открытые пункты — те же три, что и после фазы 7, и все они за границей
v0: судьба `helicopter` (§11, ничего не блокирует), `decodeAudioData` в тестах анализатора
и перцептивный судья — v0.2–v0.3 в `ROADMAP.md`. Известные шероховатости, зафиксированные
как решения, а не как долг: статическая сборка не умеет писать в `examples/` (это dev-only
эндпоинт), а состояние банка не опрашивается периодически — проверка идёт при смене
источника, URL и по кнопке `refresh`, потому что регулярно дёргать адрес, который набрал
пользователь, — это шум.

## 16. `plate`: примитив, добавленный по измерениям, а не по плану

Первое расширение набора примитивов после v0, и повод для него — не идея, а тупик,
который стало видно в цифрах. Референс — рендер Stable Audio на промпт
`sword-clash` (*«Steel on steel: a noise strike transient plus two metallic modal
rings»*, seed 2923379959, WAV, чтобы кодек не искажал цель фита). Стенд — headless-фит
той же дифференциальной эволюцией, что в плейграунде (140×20, `anchor 0`).

### 16.1. Что упиралось

Лучшее, что даёт старый набор (`modal` + `pluck` + шум, 5 слоёв, 22 слота): **0.252**,
и поиск встаёт. Остаток всегда одни и те же две цифры: 741 мс против 1002 и −29.0 LUFS
против −17.2. Ни то, ни другое оптимизатор достать не может, потому что причина
структурная:

- у `modal` длина звона наследуется от резонаторов, `tau = Q / (pi * f)`. При потолке
  `Q 400` на 3.6 кГц это `tau` 35 мс, то есть −60 дБ за 250 мс;
- огибающая с этим **перемножается**, а не продлевает: две экспоненты `a` и `b` дают
  −60 дБ на `6.9 * ab / (a + b)`, что всегда короче каждой. В категории `impact`, где
  спад огибающей ограничен 1200 мс, секунды яркого звона не собрать вообще.

### 16.2. Что сделано

`plate <freq> [modes] [stretch] [slope] [decay] [tilt]` — банк растянутых модов, где
**длина написана временем** (t60 нижнего мода, не зависит от частоты), а `tilt`
возвращает физику: верх умирает раньше. Буфер, оба бэкенда, паритет побитовый, экспорт
одного слоя — 760 Б.

| рецепт | слои | экспорт | distance | длит. | атака | доминанта | громкость |
| --- | --- | --- | --- | --- | --- | --- | --- |
| референс | — | — | — | 1002 мс | 14 мс | 3605 Гц | −17.2 LUFS |
| `modal`+`pluck`+шум | 5 | 1894 Б | 0.252 | 741 мс | 30 мс | 3287 Гц | −29.0 LUFS |
| `plate`×2 + шум | 3 | 1505 Б | **0.179** | 949 мс | 14 мс | 3644 Гц | −18.1 LUFS |

11 дБ громкости и 200 мс длительности пришли из одного изменения, и не из того, из
которого ожидалось: звон, чья длина не привязана к высоте, можно **держать** через
`hold`, а не срезать экспонентой. Отсюда идиома, вынесенная в док параметра `decay`:
длину писать в примитив, огибающую держать плоской над ней.

### 16.3. Три гипотезы, из них две неверные — и это главный результат

- **Неверно: плотность снижает crest factor.** Ожидалось `sqrt(2*modes)` ≈ 14 дБ на
  12 модах (у референса 15 дБ). Измерено: 3 мода — 21.7 дБ, 12 — 23.4. Причина — закон
  амплитуд `1/k`: нижний мод владеет пиком, добавленные моды тише и умирают быстрее.
  **Разрыв по crest к диффузии остаётся открытым**, и следующая попытка не должна
  повторять эту.
- **Неверно: положение спектра можно задать `bp` на слое.** Фит упорно ставил
  доминантный партиал на 1800 Гц (ровно половина цели) — скат 12 дБ/окт не перебивает
  6 дБ преимущества фундаментала. Пришлось добавить `slope` (закон `k**-slope`): на
  банке 600 Гц из 16 модов средний центроид идёт от 832 Гц при `slope 2` до 2942 Гц при
  `slope 0`. Это и есть управление спектром внутри банка.
- **Верно и дорого: моды выше Найквиста нельзя рендерить.** Первая версия фитилась к
  центроиду 4.6 кГц против цели 3.1 целиком на свёрнутой энергии (`plate 3600Hz
  stretch 1.4` кладёт мод №4 на 113 кГц). Теперь такие моды выбрасываются и не входят в
  нормировку, поэтому `freq`, `stretch` и частота дискретизации вместе решают, сколько
  из `modes` слышно.

### 16.4. Что осталось

- **Слепая зона метрики подтвердилась численно.** Свободный фит доходит до **0.163**,
  но с доминантным партиалом на 1800 Гц вместо 3605 — то есть метрика согласна
  обменять «тот же объект» на лучшие остальные члены. Приходится ограничивать диапазон
  слота руками. Это аргумент за перцептивного судью из `ROADMAP.md` и за пересмотр весов
  (`peakHz` 0.2 против `centroid` 0.2 + `envelope` 0.2 — их сумма перевешивает).
- **Остаточная разница теперь в шуме, а не во времени.** flatness 0.0007 против 0.0616 и
  noiseRatio 0.0024 против 0.0488: рендер слишком чистый. Тихий шумовой слой
  перелетает цель (0.23), значит нужно что-то между — расстройка модов между собой
  (биения) или шумовое возбуждение банка. Это следующий шаг, если он понадобится.
- **Порядок директив в `humanReadableDiff` вводит в заблуждение.** Он сортирует по
  драматичности в децибелах: «14 дБ тише» стоит первым при весе loudness 0.05, а
  `centroid`/`envelope`/`peakHz` по 0.2 — ниже. Стоит сортировать по `вес × ошибка`.
- **mp3 как цель фита искажает профиль.** Тот же рендер в mp3 320k против WAV: атака
  28 мс против 14, flatness 0.0224 против 0.0616. Для прослушивания и A/B mp3 годится,
  для фита цель должна быть WAV — стример в плейграунде отдаёт `--format` по умолчанию
  из `run.py`, так что менять надо там, если это станет мешать.

## 17. `txt2sfx-bridge claude` — CLI Claude Code как модель плейграунда (2026-08-08)

Направление B (плейграунд → агент) до сих пор требовало агента на том конце: либо
MCP-сессию, которая не забывает звать `sfx_next_request`, либо клиента с `sampling`,
которого сегодня почти ни у кого нет. Новый режим убирает агента из этого направления
совсем: `npx txt2sfx-bridge claude` сам собирает припаркованные задания и отвечает на
каждое запуском бинарника `claude`, уже стоящего на машине. Кнопка «Генерировать» с
провайдером `agent` начинает работать без MCP-клиента, без конфига и без перезапуска —
ключа по-прежнему нет нигде, отвечает та подписка, под которой CLI залогинен.

### 17.1. Решения и что отвергнуто

| решение | почему так, а не иначе |
| --- | --- |
| **подпроцесс, а не `@anthropic-ai/claude-agent-sdk`** | у `packages/bridge` ноль runtime-зависимостей, и именно это делает `npx txt2sfx-bridge` работоспособным (один файл бандла). SDK — второе дерево зависимостей ради `spawn`. Тот же аргумент, что в §14.2 про провайдеров на `fetch`. |
| **системный промпт файлом (`--system-prompt-file`), диалог в stdin** | контракт ≈ 14 КБ по факту замера, а Windows режет всю командную строку на 32767 символах. Промпт в argv — это баг, который проявляется только на чужой машине. В argv не попадает ничего, что читает модель. |
| **`--tools ""`** | это не сессия агента, а одно завершение: просят один блок с рецептом, а на запрос разрешения в конце пайпа отвечать некому. |
| **`is_error` проверяется отдельно от кода возврата** | отказ, исчерпанный бюджет и проблема с авторизацией приходят как *успешный* запуск с объяснением в `result`. По коду возврата это выглядело бы как ответ модели, и плейграунд стал бы парсить сообщение об ошибке как soundline. |
| **`PATH` × `PATHEXT` разбирается вручную (win32)** | `CreateProcess` сам дописывает `.exe`, но не умеет запускать `claude.cmd` из npm-установки. `shell: true` решил бы это одним флагом и отдал бы аргументы шеллу без кавычек — а во временном пути с `--system-prompt-file` пробел появляется у любого пользователя с пробелом в имени. Поэтому шим ищется сам и запускается через `cmd /d /s /c` с квотингом от Node. |
| **воркер последовательный** | хаб по построению держит одно задание, а `nextRequest` идемпотентен и может выдать его дважды — защита от второго запуска `claude` на то же задание обязана жить на этой стороне. |
| **ошибка завершения = `fail` задания, а не молчание** | плейграунд висит на `agent.complete`; молчание выглядит как зависший мост, а `fail` показывает человеку причину. |

### 17.2. Что проверено и чем

Тесты (`packages/bridge/test/claude.test.ts`, 16 штук) идут через подставной
`CommandRunner`: проверяется форма обмена — что в argv, что в stdin, что делает отказ с
припаркованным заданием, — и ничему из этого не нужны модель, сеть и чужая подписка.
Существование самих флагов тест проверить не может: они сверены с `claude --help`
руками, поэтому собраны в одной функции `claudeArgs`, и слишком старый CLI упадёт на
первой генерации со своим же сообщением про неизвестный флаг.

Живьём проверено дважды: реальный `claudeCompleter` на настоящем системном промпте
(14 414 Б) вернул рецепт за 13.6 с, и режим целиком подцепился к уже запущенному
демону, увидел припаркованное задание и отправил его в CLI.

**Наблюдение, которое стоит записать:** в живой пробе модель написала
`bp ~1.6kHz[900..3000]` — старт слота в килогерцах, границы в герцах. Валидатор ловит
это ровно так, как и задумано («slot start 1.6 is outside its range»), и дальше работает
обычный виток ремонта. То есть первый ответ CLI ничем не привилегирован — он проходит
тот же путь, что ответ любого хостед-провайдера.

### 17.3. Что осталось

- **Версия CLI не проверяется по возможностям, только по факту запуска.** `--version`
  спрашивается на старте (чтобы отсутствие бинарника не выяснялось после нажатия
  «Генерировать»), но набор флагов не сверяется. Если Claude Code переименует
  `--system-prompt-file`, это выяснится на первой генерации.
- **Один процесс `claude` на одно задание.** Кэш промпта между витками ремонта не
  переиспользуется: `--resume` дал бы это, но привязал бы мост к сессиям CLI, а
  плейграунд и так шлёт весь диалог целиком.
- **В плейграунде режим виден только во вкладке Claude Code диалога моста.** Провайдер
  `agent` про него не знает и по-прежнему говорит про поллинг, если ответить некому.

## 18. Референсная модель переехала в мост (2026-08-08)

Stable Audio Open Small — это *цель*, к которой подгоняется рецепт, и самая полезная
вещь на машине: найти запись «ржавая калитка открывается, потом тяжёлая щеколда» руками
— это медленный шаг каждой сессии. До этой правки она была доступна только из
`vite dev` через плагин, который запускал `test/stable-audio/run.py` из клона
репозитория. То есть единственная функция, которой нужна локальная машина, была
единственной функцией, которой не могло быть у хостед-плейграунда.

Теперь ей владеет мост. Аргумент за мост и аргумент за эту функцию — один и тот же: код,
который обязан выполняться на машине человека, вызываемый со страницы, которую мы не
хостим. Мост уже локальный демон, уже ставится одним `npx`, и в нём уже живут рендерер,
оптимизатор и инструменты агента.

**Запрет из §2 не нарушен.** «Никаких облачных text-to-audio моделей в ядре» — это
по-прежнему так: в `core` ничего не добавилось, модель никуда не ходит через нас, веса
лежат на диске пользователя, и результат её работы — референс для сравнения, а не
поставляемый артефакт.

### 18.1. Решения

| решение | почему так, а не иначе |
| --- | --- |
| **`run.py` кладётся в npm-тарбол** (`scripts/pack-assets.mjs` → `dist/stable-audio/`) | у пользователя нет этого репозитория — это и есть весь смысл `npx`. Альтернатива «вшить питон строкой в бандл» — вторая копия файла, который лежит в гите, и она разъедется первой же правкой. Копия, а не бандл: esbuild нечего делать с `.py`. |
| **рабочая папка ≠ папка со скриптом** | `run.py` строит venv рядом с собой, а «рядом с собой» в кэше npx — это каталог, который может исчезнуть между двумя запусками. Поэтому скрипты копируются в `~/.txt2sfx/stable-audio/`. Из клона рабочая папка — сам `test/stable-audio`, чтобы venv из терминала и venv из вкладки были одним venv, а не двумя копиями по пять гигабайт. `TXT2SFX_STABLE_AUDIO_DIR` перекрывает оба варианта. |
| **вкладка ставит модель — то, что раньше было отвергнуто** | отвергался *спиннер*, а не загрузка: «1.7 ГБ и лицензионный гейт за крутилкой в браузерной вкладке — неправильная форма». Сейчас на экране видно, что будет скачано, куда именно, ссылка на лицензию, поле токена и каждая строка, которую печатает установщик. Прятать нечего — значит, и повода отказывать нет. |
| **`run.py --provision` вместо провижининга на TypeScript** | что значит «установить» — знает `run.py` (uv, CPython 3.10, выбор CPU/CUDA-колёс, отпечаток `requirements.txt`, гейт весов). Повторить это в Node — второе определение той же вещи. Флаг ставит venv и скачивает веса, ничего не рендерит. |
| **`model.*` по сокету, а не по HTTP-роуту** | сокет уже открыт (это по нему ходит `agent.complete`), уже проходит проверку токена и Origin, и по нему уже умеют летать события — а установка на минуты без потока строк выглядит как зависание. `model.log` уходит **только тому табу, который спросил**: чужая установка, скроллящаяся в соседнем окне, — это шум. |
| **дедлайна в хабе нет** | дедлайн у ребёнка: десять минут на рендер, два часа на установку. Второй, более короткий, в хабе превратил бы медленную закачку в загадочный обрыв. |
| **токен — в окружении ребёнка, не в argv** | argv возвращается в событии `start`, виден в списке процессов любому другому пользователю машины и попадает в лог того, кто его пишет. Живёт токен один запрос и нигде не сохраняется — то же правило, что `lib/keystore.ts` описывает для вставленного API-ключа. |
| **размеры считаются обходом каталогов, а не берутся из таблицы** | «примерно 1.7 ГБ» рядом с наполовину скачанным файлом хуже, чем ничего. Симлинки не разыменовываются: HF-кэш линкует блобы в снапшоты, и обход по ссылкам показал бы 3.4 ГБ на чекпоинт в 1.7. |
| **плагин Vite остался, но стал шимом** | иначе `pnpm dev` потребовал бы второго терминала ради правки одной панели. Свой `spawn` в нём был бы вторым определением argv и лицензионного гейта — теперь оба конца зовут один модуль. |
| **панель — три экрана, а не один с предупреждением** | у большинства посетителей честное состояние вкладки — «у вас этого нет». Форма рендера с выключенной кнопкой сообщает, чего человек не может, не сообщая, что нажать. |

### 18.2. Что проверено и чем

`packages/bridge/test/stable-audio.test.ts` (25) — граница с `run.py`: argv из
недоверенного тела, разрезание строк по `\r` (прогресс-бар качалки — это он), обе
машиночитаемые строки (`txt2sfx-result`, `txt2sfx-provisioned`), раскладка HF-кэша,
выбор рабочей папки и запись установщика в папку, где его нет. `hub.test.ts` (+5) —
проводка `model.*`: base64 в ответе, события только спросившему табу, слова ошибки
как есть, `unsupported` для моста без установщика.

Живьём проверена та самая ветка, ради которой всё делалось: бандл esbuild плюс
`dist/stable-audio/` скопированы в пустой каталог вне репозитория, и `doctor` оттуда
сообщил `model needs-venv`, рабочую папку `C:\Users\…\.txt2sfx\stable-audio` и
правильный каталог кэша весов. Сама установка (несколько гигабайт) в тестах не гоняется.

### 18.3. Что осталось

- **Рендеры из `out/` по мосту не читаются.** Список файлов, которые оставил терминальный
  запуск, в статусе есть, а метода «дай мне вот этот» — нет; в дев-режиме он тянется
  роутом `/out/<name>`. Стоит `model.read`, если список кому-то понадобится.
- **`--cpu-torch` наружу не выведен.** В `provisionArgs` он есть, панель его не
  показывает — на GPU-машине это разница в ~3 ГБ загрузки, и однажды кто-то захочет
  выбрать.
- **Проба интерпретатора кэшируется на 30 с.** Компромисс: четыре запуска процессов на
  каждый `status`, и при этом «поставил uv и нажал снова» обязано сработать.

### 18.4. Найденное при релизе 0.2.0: `npx` из тарбола ничего не делал

Смоук-тест воркфлоу («поставить тарбол в каталог, который никогда не видел этот
репозиторий, и запустить `doctor`») поймал то, ради чего он и написан, и находка
касается уже опубликованной 0.1.0.

Часовой в конце `cli.ts` сравнивал `import.meta.url` с `process.argv[1]`. На POSIX npm
кладёт бинарник в `node_modules/.bin` **симлинком**, а ESM-загрузчик Node разыменовывает
симлинки, прежде чем выдать модулю его собственный URL. Пути не совпадали никогда,
`main()` не вызывался, и `npx txt2sfx-bridge` завершался с кодом 0, не напечатав ничего.

Почему это не всплыло раньше: на Windows npm пишет `.cmd`-шим, который передаёт
настоящий путь, поэтому на машине разработчика всё работало. Ровно та разница платформ,
которую локальная проверка скрывает по построению.

Форма отказа — худшая из возможных: не исключение, не ненулевой код, а быстрая тихая
успешная команда. Искать в такой ситуации нечего — нет ни строчки, по которой можно
загуглить. Поэтому исправление (`realpathSync` над `argv[1]`) закрыто тестом
`packages/bridge/test/cli.test.ts`, который ходит **через симлинк**: это форма
настоящей установки, и единственное место, где её не случается, — машина разработчика.
